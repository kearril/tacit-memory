# TacitMemory 决策记录

本文档记录当前有效的设计决定：定了什么、为什么、没选什么。决定被推翻时就地改写，不保留取代链；已失效的决定不在这里。系统具体怎么运作见 `docs/design.md`。

## 记忆的组织

### 文件是唯一真相源

- **决定**：所有记忆都是 Markdown 文件，放在独立的 Git 仓库里。检索索引只是派生缓存，可随时删除重建；换嵌入模型、换索引引擎、改表结构时一律重建，不做迁移。
- **理由**：用户必须能直接读、直接改自己的记忆，并能用 Git 看演进历史，记忆系统不能是黑盒。
- **没选**：以数据库为主存储、文件只作导出（如 Mem0、Hindsight）——用户无法直接编辑，历史锁在数据库里。

### 按生命周期组织：捕获、整理、供给

- **决定**：记忆的工作流分为三段，每段有唯一负责方。捕获：主会话在对话中写入活动、细节页与画像候选。整理：用户触发 `tacit-consolidate`，主会话依据服务准备的材料写入汇总、重写主线近况并起草画像提案。供给：服务按确定性规则将记忆交给主会话（常驻区块、服务端说明、`recall`）。
- **理由**：写入求快，整理求准；对话中的写入允许粗糙，质量由整理兜底。早期按「进入上下文的方式」分层时，难以明确各层的写入者与加载时机，实际验证中部分层级长期未能运转。
- **没选**：按内容类型分层（画像层、时间线层、项目层），每层各自决定注入方式——类型与进入方式耦合，反复派生出边界问题。

### 主线是唯一的聚合单位

- **决定**：主线（`workstream`）指「一件持续进行、由多个会话围绕它聚合而成的事务」，不分类型，不要求关联代码仓库。每条主线包含背景说明（基本不变）与近期摘要（仅在整理时更新）。主线仅在整理阶段经用户确认后成立：提示词要求写入时只使用已成立的主线名，无法匹配时细节页放入专题（slug 以事项名开头），活动不标注主线；整理阶段将首段相同的专题页提议为新主线。服务不拦截未成立的新名称，其写入与检索照常工作，但不进入常驻区块，由整理报告列出供后续处理。一条活动只属于一条主线。
- **理由**：服务器运维这类没有代码仓库的长期事务，在「项目」模型下只能散落在专题中，而细分类型只会导致类别不断膨胀。由于主线进入每个会话的常驻区块，模型临时构造的名称不应直接占据该位置，否则容易产生同义分叉并加重整理负担。服务端拦截新名称会打断正常记录，因此只在提示词层面约束。
- **没选**：项目加「近期主线」两个概念（近期主线容易演变为与活动重复的流水账）；英文采用 `mainline`（在代码语境中常指主干分支）；允许细节页用未成立主线名建目录再靠整理收敛（分叉率高，合并成本大）。

### 画像分作用域，以会话内即时确认晋升

- **决定**：画像条目分为三种作用域：全局（进入常驻区块）、`workstream:<名>`（进入主线简报）、`domain:<标签>`（常驻区块只放一行索引，正文按需读取）。一条规则至少在两类不同情境下成立才归入全局。晋升有两个入口：用户纠正 Agent 或明确提出协作做法时，Agent 仅询问一次「要记成长期规则吗」，同意后直接写入；其余观察记为候选，在整理时归纳成提案由用户一次批量确认。
- **理由**：约半数候选仅在特定情境下成立，全部常驻会引入上下文噪声。早期曾尝试按「出现天数」自动触发晋升，但随着 Agent 遵循度提高，用户不再重复纠偏，出现天数信号随之衰减，实测中长期无候选能够达到门槛。
- **没选**：为每个领域生成独立 skill（链接管理复杂，且触发可靠性并不更高）。

### 机器身份与写明适用条件，而非按机器或客户端分片

- **决定**：每台机器在 `config.yaml` 中具有名称与可选说明（缺省由主机名规整而来），常驻区块在 `<user_memory>` 开头输出一行机器行；记忆规则要求与环境有关的条目在正文中写出机器名而非「本机」「这里」，机器清单记入画像「档案」；服务端不按机器或客户端分别渲染常驻内容，检索也不按机器过滤。
- **理由**：多端共用同一份记忆库时，隔离的关键在于把适用条件写清，而不是在存储或常驻区块里增加 `machine:`/`client:` 作用域标签；常驻区块在开头给出本机身份后，Agent 结合上下文相关性就能判断各条环境记忆是否适用于当前机器。
- **没选**：为画像条目或页面小节引入 `client:<名>`、`machine:<名>` 作用域标签；按绑定或客户端分别渲染不同的常驻区块；由服务单独维护机器清单或强制按机器过滤检索结果。

### 细节页分四种类型

- **决定**：细节页必填 `type`：`incident`（排错）、`decision`（决定）、`entity`（实体）、`work`（工作记录）。服务只校验取值，不校验小节名；只按英文名识别三个约定小节：`work` 页的 `Leftovers` 汇总为主线的未决事项，`decision` 页的 `Overturned` 非空时该页不算有效决定，`incident` 页的 `Lesson` 在整理报告中引用。
- **理由**：主线简报须按类型分组，使 Agent 在开局即可快速识别有效决定、排错记录与未决事项。小节结构由内容决定，强制校验会导致写入僵化。
- **没选**：只有三种类型（最常见的「一段工作的完整记录」无处可放）。

### 条目用内容哈希短码引用

- **决定**：服务返回条目时附带短码（规范化文本哈希的前 6 位），后续调用凭短码引用；短码不写进文件。内容一改短码即失效，这同时充当乐观并发控制。
- **理由**：条目级引用都是短时的（一次往返或一次整理），长期引用只发生在细节页之间，已由页面标识解决。
- **没选**：文件内写永久编号（手改要维护）、按原文匹配（转述易失配）、按行号（插入即错位）。

### 不设写入上限，整理时提示篇幅

- **决定**：画像、领域、活动、标题与别名都不设长度与条数上限。简洁由两处保证：提示词写明每种内容的形状；整理报告列出超过 `consolidation.hintEntryLength` 的条目与超过 `consolidation.hintResidentLength` 的常驻区块，只提示不拒绝。保留的只有结构性规则（活动与触发描述限一行）、主线简报上限与别名最少个数。
- **理由**：拒绝写入的代价落在记录那一刻，而那一刻最不该被打断；模型为挤进上限反复改写，或被拒后放弃记录。上限数字当初凭感觉定，没有数据支持。

## 写入与整理

### 不用钩子，不做后台补抽

- **决定**：写入只有三个入口：记忆规则（主会话在对话中当场写）、用户触发的 `tacit-remember`、整理 `tacit-consolidate`。不使用任何客户端钩子，也不在会话结束后读会话记录补抽。
- **理由**：主会话是唯一真正理解当前情景的一方，知道哪句是拍板、哪次是纠正。事后补抽只看到脱离情景的记录，抽出的多是噪声。钩子覆盖不了「即将退出」与轮中途的自动压缩，每个客户端还要单独接入，会陷入兼容地狱；只依赖 MCP 与 skill，接入新客户端不需要额外工作。
- **代价**：主会话没遵守规则、用户也没执行 `tacit-remember` 就结束会话时，这段内容不会被记住。

### 服务不调用生成模型

- **决定**：服务不调用任何生成式对话模型，包括后台汇总、抽取与反思。写什么、怎么写、汇总与主线、画像提案全部由主会话完成；服务只做存储、校验、判断与检索。整理时服务只备料（周活动原文、候选与原话、变化过的页），不写提案。
- **理由**：主会话掌握完整上下文，判断质量最高，即使是空白上下文的会话也比小模型好得多；服务没有自己的「大脑」，行为可预测、可测试。
- **没选**：服务内置 LLM 做抽取、合并或重要性打分（如 Mem0、Hindsight、Generative Agents）。

### 决策模型只做判断

- **决定**：决策模型只回答结构化的选择题（是否同一页、同主题、同一偏好、规则冲突），返回概率，按两个阈值划为「确定 / 不确定 / 否定」三档。不确定时不自动处理，留待整理复核。凭据检测不交给它，只用本地正则。
- **理由**：判断可预测、可测试。若将凭据检测交给外部模型，恰恰在写入真实含凭据时将其外泄，与安全目标相悖；同时还会为每次写入增加约 2 秒延迟。
- **实测**：基于 TypeSafe `jev-latest` 以中文真实样本标定的默认阈值为确定 ≥ 0.85、否定 ≤ 0.25：重复页正样本概率最低 0.90，负样本最高 0.19，误拒为 0。更换其他决策模型后默认阈值可能不再适用，须由使用者自行核对并调整。
- **代价**：口述式的「密码是 …」等缺乏格式特征的裸值无法通过正则拦截，依赖工具说明中「禁止写入凭据」的规则约束。

### 整理分三阶段，按变化增量检查并限时

- **决定**：整理先自动完成格式修正、清理确定重复的候选、写周与月汇总、重写主线；再把画像提案、页面重组、冲突条目编成编号清单，用户一次回复；最后执行并以 `consolidate:` 提交。依赖决策模型的检查只看上次整理以来变过的内容；判断的概率按提问内容缓存，改阈值不使缓存失效；一次整理最多等模型 20 秒，到点照常出报告，没算完的下次接着算。
- **理由**：确认成本压到一次回复。用户判定「这两页不重复」后，只要两页不再改就不会再报，不需要另维护「不重复名单」。调用量与两次整理之间的写入量成正比，而非与仓库总量成正比。有的客户端对单次 MCP 请求只等 30 秒，模型一旦挂起，不限时会让整份报告被丢弃。
- **没选**：每次全量检查加「已判定不重复」名单（又一个要手动维护的文件）；空闲时后台预算（等于后台补抽）。

### 只有完整整理推进基准

- **决定**：报告开头写明是否完整（判断在预算内由可用的模型算完、没有类别被截断；未配置的模型不算不完整）；只有基于完整报告、且用户没有限定范围的整理以 `consolidate:` 提交，其余以 `consolidate(partial):` 提交，不推前基准。基准以来的增量类别全部列出，不受每类 20 项的上限。
- **理由**：限定范围、预算用完或截断时照样推前基准，之后基准以来的页、原话与教训就再也不会出现在报告里；多台机器共用一份记忆时，一台上的不完整整理会让两台都漏掉。增量不截断，是因为基准不推前时，截断会让每次只露出同样的前 20 项。
- **没选**：服务记录每一类处理到哪里（又一份要维护的状态）；让不完整的整理也推前基准、靠下次全量补查（增量检查就失去意义）。

### 记忆指令是手动 skill，整理报告经 MCP 资源提供

- **决定**：`tacit-remember` 与 `tacit-consolidate` 是只能由用户触发的 skill，与记忆 skill 一样由服务生成、由 `connect` 链接进客户端的 skill 目录。整理报告要现场计算，经资源 `tacit://consolidation-report` 读取。
- **理由**：MCP prompt 的参数在有的客户端里只能写成 `名=值`，后面跟的文字会被丢弃；手动 skill 触发时附上的文字原样送达。资源不占工具列表、不进开局上下文，模型也不会在用户没要求时去读。
- **没选**：保留 MCP prompt；新增返回报告的工具（每个会话都占说明，且可能被模型擅自调用）；让 Agent 经 shell 调 CLI（依赖它有 shell 且 `tacit` 在 PATH 上）。

### 是否该整理只作为信号对外提供，由客户端决定何时询问

- **决定**：服务经 `GET /api/consolidation` 与 `tacit consolidation` 只回答「是否该整理」，不附原因与计数；判断与服务端说明末尾的整理提示同一份，每次请求时现场计算，不调用模型。何时询问、得到答案后做什么（提醒用户、开会话运行 `tacit-consolidate`），由客户端自己的定时任务决定。
- **理由**：整理提示只在客户端连接时下发一次，会话开得少或开得久都会错过；不少本地 Agent 能自己配定时任务，服务给出信号即可，不必替各客户端安排时机。只答一个布尔值，是因为定时任务只需决定要不要打扰用户，细节在整理时由报告给出。现算的成本与 `tacit status` 相同，没有缓存就不会给出过时的答案。
- **没选**：服务定时计算并缓存（多一个定时器，答案可能已过时）；服务主动推送到 webhook 或系统通知（要另设通知配置）；MCP 通知（所用客户端基本不展示）；返回原因与计数（没有使用方）。

## 注入

### 常驻区块与服务端说明按变化频率分路

- **决定**：只在整理时变化的内容写进客户端上下文文件里的常驻区块：全局画像、领域索引、主线（最近 28 天有活动的主线显示近况）。每天变化的内容在客户端连接时现场生成为服务端说明：核心规则、值得记标准（固定部分不超过 3000 字符）、最近 7 天的活动、状态与整理提示，总长不超过 4000 字符，超出时从最早的活动截起。常驻区块声明自己是「可能过时的记忆」，优先级低于项目上下文与当前对话。
- **理由**：服务端说明在主流客户端里约有 4000 字符的上限，装不下画像；全部写进客户端文件又要每天重写用户的全局文件。核心规则留在服务端说明，服务停止时规则随工具一起消失。
- **代价**：主线的活跃与否随日期变化，常驻区块每天至少重渲染一次（内容没变时不写文件）。

### 提示词分层，策略文字外置

- **决定**：给主会话的文字分三层：核心规则在服务端说明里，开局可见；详细写法做成记忆 skill，开局只占名称与描述，写入时才读正文；调用格式只写在工具说明与拒绝回复里。策略类文字外置为 `TACIT_HOME/prompts/` 下的四份提示词文档，用户可整份替换（`skill.md` 只能追加写法约定）。提示词的改动以日常使用中的摩擦点为依据，改后在真实客户端里复现验收。
- **理由**：固定部分的容量一直被写法细节挤占；触发条件必须开局可见，写法细节只在写入时需要，skill 恰好满足「列表常驻、正文按需」。离线小样本自动评测区分度低且耗时长，已不再使用。
- **没选**：在 `AGENTS.md` 里另加托管区块（每个会话都占上下文）；经 MCP 资源提供 skill（客户端读不到描述，不列进系统提示）；让用户编辑整份 skill（会改坏触发描述）。

### 给 Agent 的文字一律英文

- **决定**：只给 Agent 看的文字（工具说明、服务端说明、skill、工具回复、整理报告、发给决策模型的问题、值得记标准的内置默认）固定英文；记忆文件的结构词与 `init` 写出的骨架也固定英文，只认这一种写法；`language` 只决定记忆内容用什么语言写、给人看的显示（Web 界面、CLI 输出、API 错误说明、日志）用什么语言。CLI 的帮助与用法错误固定英文。页面只识别 `Lesson`、`Overturned`、`Leftovers` 三个小节，其余小节名是内容。
- **理由**：长提示词只维护一份，避免两种语言的措辞漂移；英文指令的遵循错误率更低。格式与语言无关，解析器只认一种写法，不同语言的机器之间导入记忆不需要转换；Web 把被识别的小节名显示为本地化标签，用户在界面里看不出差别。
- **没选**：界面语言与记忆语言分设开关（仍只有一个语言概念）；要求页面的全部小节名用英文（自由取名的小节是内容，按记忆语言写更自然）。

## 存储与索引

### 索引用 SQLite：FTS5 加 C# 计算向量距离

- **决定**：派生索引用 SQLite，全文用 FTS5（中文在 C# 里切成相邻两字一组，每段末尾的字另作一个词，让单字查询能按前缀匹配）。向量以 float32 原样存成 BLOB，放在普通表里；检索时先用 SQL 按筛选条件选出单元，再在 C# 中逐个计算余弦距离，取最近的若干个。
- **理由**：个人记忆只有几百个单元，逐个计算一次远不到 1 毫秒，用不上任何近似索引。原生扩展 sqlite-vec 只被用来逐条计算距离，却要为它付出三个平台各一份二进制文件、SHA-256 校验、两处构建目标、发行包里多一个原生文件、启动时多一种失败方式，以及「支持哪些平台由它决定」的限制。Turso 的 .NET 包向量可用但开不了全文检索，改用它就要自写倒排表与 BM25。
- **没选**：保留 sqlite-vec 并改用它的 `MATCH … AND k = ?` 与元数据列（个人规模下同样是全量扫描）；引入向量运算的 NuGet 包（普通循环已经够快）。
- **实测**：部分轻量级 reranker（如 0.6B 参数量模型）对同主题但不相关的页面仍可能给出较高分数（如实测中的 0.667），`minRerankScore` 难以单独截断此类噪声，因此默认仅设为 `0.001` 以过滤极低分，结果质量主要依靠 RRF 融合与 `topK`。

### 云端备份用 WebDAV，密钥用固定环境变量名

- **决定**：云端备份把整份备份上传到一个 WebDAV 目录，只在用户要求时上传；远端只存一份，先上传成 `.part` 再 MOVE 覆盖，服务不支持 MOVE 就报错。每个密钥有固定的环境变量名（`TACIT_*_API_KEY`、`TACIT_WEBDAV_PASSWORD`），环境变量非空时优先，否则用配置里的明文。
- **理由**：坚果云、群晖、Nextcloud 与自建服务都提供 WebDAV，一个 URL 加用户名密码即可。Git 推送只带走记忆仓库，丢掉配置与提示词；上传整份备份，恢复路径与本地完全相同。只存一份使远端占用固定，`.part` 加 MOVE 保证上传中断时旧备份完好。固定变量名让报错与 `status` 都能写出确切的名字。
- **没选**：`git push` 到远端仓库；远端按日期轮换多份（各家 WebDAV 行为差异大）；配置里用 `${VAR}` 插值；系统钥匙串（跨平台不一，后台服务可能拿不到）。

### 多台机器经 git 同步整个记忆仓库

- **决定**：多台机器共用一份记忆，靠给记忆仓库配一个 git 远端：每台机器各跑自己的常驻服务，写入前拉取、写入后推送、定时拉取。只同步记忆仓库，配置、提示词文档、绑定与备份留在各自机器上。tacit 只接受一个 git 地址，认证全交给 git，不保存凭据。
- **理由**：记忆仓库本来就是 git 仓库，文件是唯一真相源，git 是现成的、能离线工作的同步与合并工具。两台机器同时写同一处的机会很小（一个会话只写三四次），冲突是例外而不是常态。各机器的模型端点、端口与路径不同，配置不能同步。
- **没选**：导出、导入记忆（每次要手动挑内容，也要处理两边都改过的条目，等于再造一遍合并）；一台机器跑常驻服务、其他机器远程连它（那台机器离线或断网时其他机器全不可用，MCP 端点也要对外开放）；同步整份备份（备份是快照，没法合并两边的改动）。

### rebase 而不是合并提交；union 只给只追加的文件

- **决定**：两边都有新提交时把本机的提交 rebase 到远端之后，历史保持一条直线；冲突就放弃这次 rebase、暂停自动同步，由主会话在整理时解决。不用 `--autostash`；有未提交的手改挡路时这次什么都不做。`recent/*.md` 与 `candidates.md` 用 union 合并，画像、主线文件与页面不用。合并与换行规则（含 `* text=auto eol=lf`）每次同步写进 `.git/info/attributes`，不提交 `.gitattributes`。
- **理由**：整理基准与日志均按提交历史定位，线性历史最便于追踪；服务产生的提交均为单文件小提交，rebase 极少发生冲突。`--autostash` 在弹出暂存发生冲突时会向工作区文件写入冲突标记。只追加文件各自新增几行，`union` 策略可同时保留双端记录；替换类修改在 `union` 下会同时留下新旧两行，因此其余文件遇冲突时暂停并交由人工处理。将规则写入 `.git/info/attributes` 可对已有及新克隆仓库立即生效，无需额外提交，也能约束手动执行的 git 命令；Windows 上的 `core.autocrlf` 会将检出文件转为 CRLF，从而误触发文件监听与未提交改动检测。
- **没选**：合并提交（历史分叉，整理基准难找）；冲突时自动取一边（悄悄丢掉另一台机器的记忆）；把 `.gitattributes` 放进 `init` 骨架提交（已有的仓库要补一次提交，补之前的同步不受保护）。

### 恢复后暂停同步，由用户选边

- **决定**：开启同步时，恢复备份成功后同步暂停（重启后仍暂停），连 `tacit sync` 也不动，直到用户选边：`--use-local` 以本机为准强推（`--force-with-lease`），`--use-remote` 先做一份手动备份再重置到远端并重建索引。历史不相关与冲突时同样可以选边。选边只在 CLI 与管理 API 提供，Web 只显示命令。
- **理由**：恢复让本机回到过去，接着自动同步要么会把另一台机器后来写入的记忆覆盖，要么把刚恢复的内容盖回去，哪一边都不该由程序替用户决定。选边会丢掉一边的提交，先预览、再确认，和 `restore` 一样。
- **没选**：恢复后自动强推（另一台机器的新记忆悄悄消失）；恢复后照常同步（rebase 会把恢复前的提交又带回来）。

## 辅助模型

### 按通用协议接入，全部可选

- **决定**：三个辅助模型按通用协议接入：嵌入用 OpenAI Embeddings，reranker 用 Cohere/Jina Rerank，决策模型用 System One。另外只为值得支持的提供方做适配，目前只有 Cloudflare Workers AI。地址填完整请求 URL，程序不追加路径。三个模型都可以不配置，缺席时按降级处理；密钥也都可以不写。
- **理由**：作为开源项目，不能假设用户会自己部署模型。Cloudflare 的免费额度让新用户不自部署、不付费就能用齐三类模型。同一协议在不同服务上路径不同，只有完整 URL 不受路径约定影响。三个都必须配置的话，新用户拿到服务之前根本无法试用。
- **没选**：每家提供方都做适配（每加一家都要跟进格式变化）；把模型接口层改写成 Python 子服务（多一个运行时与常驻进程，而格式适配几十行 C# 就够）。
- **代价**：判断阈值不随模型调整，换模型后的质量由用户自行核对；判断缓存不含模型名，换模型后要 `tacit reindex` 清空。

## 服务与客户端

### 单一常驻 HTTP 服务

- **决定**：只以一个常驻的 HTTP 服务运行，所有客户端连它，写入在服务内串行。不提供 `stdio` 传输。任何界面（CLI 的部分命令、Web 界面）也只调用常驻服务，不直接读写记忆仓库。
- **理由**：用 `stdio` 时每个客户端各起一个进程，会同时改同一批文件、同时 `git commit`，迟早互相覆盖或撞上 Git 锁。单一写入方从根上消除这些问题。
- **代价**：服务未运行时记忆工具不可用，靠托管工具常驻。

### 绑定不区分客户端，不代写 MCP 配置

- **决定**：绑定只由名称、上下文文件与 skill 目录组成，名称只是标签。tacit 只维护常驻区块与 skill 链接，不读写任何客户端的 MCP 配置，`connect` 只打印端点。多个绑定可共用同一个文件或目录。上下文文件所在的目录与 skill 目录不存在时新建，并在结果中列出。
- **理由**：TacitMemory 对客户端的要求只有三样，都是通用约定：读一个上下文文件、扫描一个 skill 目录、连一个 HTTP MCP 端点。各家真正不同的只有 MCP 配置的位置与格式，逐个适配的成本远高于用户自己加一项配置。目录不存在就拒绝，在新机器上初始化时处处碰壁（客户端往往要首次运行后才生成 skill 目录）；写错的路径会被一并新建、skill 因此静默失效，所以结果逐个列出新建的目录，交给用户确认。
- **没选**：逐个适配客户端；取消常驻区块、只剩 skill 加 MCP（服务停止时画像随之消失，且不能保证每个客户端都把服务端说明放进系统提示）；打印一段 MCP 配置 JSON 示例（各家格式不一）。

### MCP 扩展等客户端跟进后再做

- **决定**：Tasks、Skills、elicitation、Apps 等 MCP 扩展，等所用客户端支持后再实现。现在只记录每个客户端声明的能力，在 `tacit status` 与仪表盘里显示。
- **理由**：降级路径就是现有做法，现在写增强路径多得不了什么，也无法实机验收；能力记录让用户看到客户端何时跟进。

### CLI 面向脚本与 Agent，不做 TUI

- **决定**：`tacit` 的命令一律非交互、可组合：退出码分开（0 成功、1 运行失败、2 用法错误、3 配置无效、4 服务未运行），不用位置参数，结果写 stdout、错误与提示写 stderr。只在终端里提问：`restore` 要确认，非终端下不带 `--yes` 即拒绝；`init` 在没有 `--language`、也没有已有配置时询问语言，非终端下即以用法错误结束。两者都不挂起。颜色只在终端里出现，`NO_COLOR` 即关闭。
- **理由**：调用者除了用户还有 Agent、托管工具与脚本；用户日常经 Agent 使用记忆，需要界面的事由 Web 界面承担。

## Web 界面与访问

### 由常驻服务托管的静态单页应用

- **决定**：前端是仓库里独立的 TypeScript 工程，构建为静态文件，由常驻服务在 `/ui` 下托管，只经管理 API 与服务交互，接口类型由 OpenAPI 文档生成。配置的入口换成设置页：`config.yaml` 由服务整份生成、不带注释，保存后在进程内重新加载。
- **理由**：「分离」落在契约上而不是部署上，仍是一个进程，托管、备份、排障都不变。管理 API 本来就是命令行在用的入口，规则只有一份。服务在后台运行，从其他设备上无法重启它，所以配置必须能在进程内生效。配置项的解说放在界面里比放在 YAML 注释里更有用，能给出默认值与当场的校验结果。
- **没选**：带服务端渲染的前端框架（多一个常驻进程）；用 .NET 界面框架；按行修改 YAML 以保留注释。
- **代价**：`config.yaml` 里的手写注释在第一次经设置页保存时丢失；「文件始终可直接编辑」只适用于记忆与提示词文档。

### 按连接来源鉴权，允许额外监听

- **决定**：服务总是监听 `127.0.0.1`，`server.host` 给出一个额外地址。是否需要登录只看 TCP 连接的对端地址：本机免登录，其他设备访问管理 API 要登录。鉴权是一个访问密码，没有账号与权限分级；`/mcp` 只接受本机。其他设备只能到达 `/`、`/ui` 与 `/api`，其余路径默认关闭。不内置 HTTPS。
- **理由**：能够在本机运行程序的用户本就可以直接读写 `TACIT_HOME`，本机鉴权并无安全收益；按对端地址区分也可使 CLI 保持零改动。对端地址由操作系统提供且不可伪造，不可信请求头不能作为依据。始终监听回环地址是因为客户端 MCP 配置与 CLI 默认指向 `127.0.0.1`。系统面向单用户个人部署，账号与权限分级只会增加复杂度。
- **没选**：全部连接都要登录（脚本与 Agent 的调用全要改，安全上没有收益）；完全依赖 Tailscale 或 SSH；内置 HTTPS（自签证书在每台设备上都要手动信任）。
- **代价**：纯局域网下密码与密钥明文传输，需要加密时改用 Tailscale 地址；反向代理转发到回环会绕过登录。

### 设置页的密钥随配置下发，按普通设置项编辑

- **决定**：配置视图带上 `config.yaml` 中密钥的值（来自环境变量的不下发），设置页把它当普通设置项：掩码显示、就地修改、清空即删除，随全页保存生效；不设单独取值的接口，失焦也不保存。
- **理由**：一个输入框、一种眼睛，含义处处相同。登录后的设备本来就能看到这些值，一起下发不扩大暴露面；保存会重新加载服务、且要整份校验，逐项失焦保存会频繁重载并在中间态报错。
- **没选**：只写不读（Grafana、Vercel 的做法，界面上无法核对已存的值）；按需单独取明文（同一行里两种眼睛与「改写」状态来回切换）；用占位串代替真实值放进输入框（未修改也可能把占位串存回去）。
- **代价**：每次打开设置页，响应里都带明文密钥，所以该响应设为 `no-store`。

### 重新加载整体重建运行时

- **决定**：常驻服务分为外壳与运行时。外壳与进程同生命周期（锁、访问控制、客户端记录）；运行时持有一切随配置而定的部件，只经一条打开路径构建。重新加载是一个维护操作：等在途读写结束，释放旧运行时，用新配置打开新的；打不开时按原配置重开。端口、额外监听地址、别名最少个数、记忆仓库位置与语言只在重启后生效。
- **理由**：打开路径已承载全部初始化与不变量，重建原样继承它们；只有一条路径，测试覆盖的也是这一条。
- **没选**：把新配置热替换进各部件（每个部件都要可变并处理并发，漏一处就半新半旧）；保存后要求重启（从其他设备上无法重启）。
- **代价**：重新加载清零模型冷却等内存状态，期间请求排队。

### 外观偏好只存在浏览器，明暗经 `<meta name="color-scheme">` 生效

- **决定**：明暗与调色盘是每个浏览器自己的偏好，存在 `localStorage`，不写进 `config.yaml`，也不经管理 API。用户的明暗选择写进页头的 `<meta name="color-scheme">`，样式据此设置 `color-scheme`，`light-dark()` 随之切换；调色盘是根元素上的 `data-palette`。`index.html` 里一段内联脚本在首次绘制前从存储恢复两者。侧边栏的明暗切换只有两态，规则见 `docs/design.md`「Web 界面」。
- **理由**：外观只关乎看的人在哪台设备、什么光线下看，与记忆和服务无关；写进配置会让一台设备的选择改掉其他设备的外观，还要经过重新加载。根上的 `color-scheme` 不依赖脚本，脚本没运行时页面照样跟随系统。两态切换覆盖「一时太亮」这种临时调整，又不会在用户不知情时固定住与系统相同的一边；确实要固定时，在调色盘菜单里取消「明暗跟随系统」。
- **没选**：存进 `config.yaml`（偏好跨设备串扰，保存触发重新加载）；用根元素上的类名或 `data-theme` 切换（样式依赖脚本，脚本没运行而系统为深色时显示错误）；常驻的三态切换（侧边栏空间有限，「跟随系统」与当前一边同时出现时容易混淆）。
- **代价**：同一台设备经不同地址打开（如 `127.0.0.1` 与 Tailscale 地址）各记各的偏好。

## 代码组织

- **一处声明，处处派生**：每个配置键只在键表 `ConfigKeys` 声明一次，加载、写出、设置页、重启比对与密钥处理都从它派生；工具参数的取值只在 Core 定义一次；前端的地址只由 `routes.ts` 构建与解析。理由：同一份事实抄在多处，迟早不一致。
- **写入只发通知**：写入工具写完文件后只通知「哪类来源变了」，索引、服务端说明、常驻区块与 skill 的刷新由派生产物维护统一决定。后台同步重试用尽时把索引标为「可能过期」，下次检索前全量同步兜底。
- **读取必须写明是否计数**：读取入口要求调用方说明是否计入使用统计；Agent 的 `recall` 计入，Web 界面的浏览与检索追踪不计入。
- **不把 git 嵌进进程**：整理仍由主会话用 `git` 命令行提交，两种实现混写同一仓库会有行为差异，所以服务也用命令行 `git`。
- **不引入 Markdown 解析库**：服务按行修改文件，要求原样保留其余字节，语法树帮不上。

## 发布

### 单文件、只裁框架的自包含发行包

- **决定**：发行包为自包含、单文件、压缩，只裁剪框架（`TrimMode=partial`）；原生库 SQLite 留在可执行文件旁。全部 JSON 经构建时生成的契约读写，裁剪分析器的警告即错误。发布前用 `build/smoke.sh` 冒烟，它是裁剪版唯一的安全网。不做 Native AOT。
- **实测**（win-x64）：依赖框架的 zip 3.8 MB 但要预装运行时；自包含多文件 55 MB、370 个文件；单文件加压缩 50 MB；加上只裁框架后 13.6 MB、解压 21 MB。启动时间不作取舍依据，服务是常驻的。
- **理由**：用户要小体积与整洁的目录。单文件解决文件多，压缩解决磁盘占用，只有裁剪能缩小下载。Native AOT 卡在 Dapper 运行时生成代码，收益不明显。
- **代价**：测试跑在未裁剪的构建上，裁掉用得到的东西只能靠冒烟发现；.NET 的安全补丁要随 tacit 重新发布才生效。

### 三个平台，各在本平台打包

- **决定**：只出 `win-x64`、`osx-arm64` 与 `linux-x64`（glibc）。打包与冒烟只用一套 bash 脚本，三个平台共用。推送到 `main` 时在 Linux 上跑全量测试；发版时 Linux 与 Windows 各跑一遍，再在三个平台各自的运行器上打包与冒烟，全部通过后汇总成一个 Release。路径是否忽略大小写按平台判断：Windows 与 macOS 忽略，Linux 区分。
- **理由**：三者覆盖主流桌面与服务端运行环境。macOS 只能在原生运行器构建时为可执行文件执行 ad-hoc 签名，而 Apple Silicon 拒绝运行未签名二进制，因此 macOS 发行包不能交叉打包。日常 CI 仅运行在最快的 Linux 运行器上（已覆盖与 macOS 共用的全部非平台专属代码路径），在发版流水线中再补充 Windows 测试与三平台各自打包，可显著降低持续集成的运行器耗时与资源消耗。macOS 默认文件系统不区分大小写，若简单按「是否为 Windows」判断路径大小写敏感性，会将同一目录误判为两处。
- **没选**：`win-arm64` 与 musl 系 Linux；`osx-x64`（Intel Mac 已停售）；PowerShell 与 bash 两套打包脚本；单机交叉打包三个平台；在每次推送时同时运行三平台全量测试（运行器成本高）。
- **代价**：mac 包未经公证，浏览器下载的包会被 Gatekeeper 拦下；只在 Windows 上出现的问题要到发版时才被 CI 发现，平时靠本机测试。

### GitHub Releases 分发，Apache-2.0 许可

- **决定**：版本号由 MinVer 从 `v*` tag 推出，1.0 之前不承诺数据兼容。推送 tag 时 GitHub Actions 构建、测试、冒烟并创建 Release，附 SHA-256；推送到 `main` 时跑全量测试。许可为 Apache-2.0，发行包附自动生成的第三方许可声明。
- **理由**：发布只有「打 tag」一个动作，不会出现 tag 与项目文件版本不一致；在干净的运行器上构建，产物可复现。Apache-2.0 与 MIT 一样宽松，另有专利授权，且不授予商标权。
- **没选**：dotnet tool（要求使用者预装 .NET SDK）；MIT（缺乏专利授权与商标条款）；AGPL-3.0（强传染性条款会增加下游集成与使用的顾虑，而个人记忆工具被改作闭源商业服务的风险极低）。
