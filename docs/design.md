# TacitMemory 设计

本文档定义系统**做什么**：记忆如何分层、何时写入、如何检索、对外表现出哪些规则。代码如何组织见 `docs/architecture.md`，术语见 `GLOSSARY.md`。

## 1. 目标

让 Agent 像一个老朋友：记得用户的喜好与偏好，记得用户最近在做什么，提起具体的事时能想起细节。

| 场景 | 用户说 | 期望的反应 | 依靠 |
| :--- | :--- | :--- | :--- |
| 新开会话 | "帮我写个脚本" | 直接按用户习惯的语言和方式回应，不用重新交代 | 画像 |
| 随口聊 | "最近有点累" | 能联想到用户最近在忙的事 | 近期摘要 |
| 提起一件事 | "上次数据库升级那个坑" | 想起当时的现象、根因和解法 | 细节页 |
| 没提起 | 聊别的 | 不主动翻旧账 | 细节页不常驻 |

## 2. 原则

1. **只存环境里拿不到的信息**：记忆只保存 Agent 无法从代码、仓库文档、配置、客户端会话历史中获得，且会改变其行为的信息。能从环境查到的不存。
2. **按进入上下文的方式分层**：
   - **常驻**：会话开始时就在上下文中，占用预算，一定被看到；
   - **按需**：Agent 主动检索，不占预算，但前提是它知道去取。
3. **常驻只能依据开局信号**：会话开始时只知道工作目录、客户端和时间。只在特定话题下才相关的内容一律按需检索，不预先猜测话题。
4. **文件是唯一真相源**：所有记忆都是人类可读、可直接编辑的 Markdown 文件，存放在独立的 Git 仓库中；检索索引是派生缓存，随时可删除重建。
5. **判断交给主会话**：需要理解和判断的工作（写什么、怎么写、如何折叠）由主会话完成；TacitMemory 只负责存储、校验与检索，不调用对话模型。

## 3. 三层记忆

| 层 | 内容 | 进入方式 |
| :--- | :--- | :--- |
| **画像** | 档案（用户是谁）+ 协作规则（`When → Do/Don't`） | 常驻 |
| **近期活动** | 近期摘要（约 10 行）+ 按月存放的完整活动记录 | 近期摘要常驻；活动记录按需 |
| **细节页** | 一件事或一个主题一页，页内事实、决策、坑点写在一起 | 按需：被提起时检索 |

## 4. 存储

```text
<记忆仓库>/
├── persona.md              # 画像
├── candidates.md           # 画像候选与拒绝列表
├── recent.md               # 近期摘要
├── recent/YYYY-MM.md       # 活动记录（按月）
├── pages/
│   ├── <项目>/<slug>.md    # 细节页，目录名即所属项目
│   └── _topics/<slug>.md   # 不属于任何项目的专题
└── .cache/                 # 派生索引，不进 Git
```

- 每次由服务完成的写入自动提交一次 Git，提交信息自动生成；从不自动推送远端。
- 用户可以随时直接编辑文件；服务感知变化并同步索引与常驻区块，但不替用户提交。

## 5. 细节页

### 线索

每页的 YAML 头保存线索，供检索命中：

```yaml
title: 数据库升级后扩展丢失
aliases: [全文检索插件失效, 升级后搜索不到中文]
dates: { first: 2026-10-21, last: 2026-10-25 }
related: [my-app/backup-script]
```

| 字段 | 作用 | 由谁写 |
| :--- | :--- | :--- |
| `title`、`aliases` | 覆盖专有名词与口语说法，参与全文与向量检索 | 主会话；必填，`aliases` 至少 2 个，否则拒绝写入 |
| 所属项目 | 筛选条件，由页面所在目录决定 | 主会话按当前仓库根目录名指定；非项目内容归 `_topics` |
| `dates` | 筛选条件：首次与最近一次涉及 | 服务自动维护 |
| `related` | 明确的关联页 | 主会话 |

- 不设自由标签，与 `aliases` 职责重叠。
- 用户用新说法命中某页、而该说法不在 `aliases` 中时，可以追加进 `aliases`：只加线索，不改正文。

### 检索

1. 查询提到项目或时间时，先按所属项目与日期筛选；
2. 全文检索与向量检索两路并行：全文负责专有名词、文件名、命令，中文两字及以上的词均可命中；向量负责口语与近义说法；
3. 合并两路结果，由 reranker 重排。

嵌入模型与 reranker 均为必需配置。

## 6. 写入

### 入口

写入只有两个入口，不使用客户端钩子，也不做会话结束后的后台补抽：

1. **记忆规则**：注入常驻区块，规定何时、如何写入，主会话在对话中当场执行；
2. **记忆指令**：`remember`，用户在压缩上下文、退出前或认为重要时执行，主会话立即整理并写入。

代价是明确接受的：主会话未遵守规则、用户也未执行指令就结束会话时，该段内容不会被记住。

### 值得记标准

默认五类，可通过 `rules.md` 定制：

1. 用户纠正或打断 Agent；
2. 方案拍板（保留用户原话）；
3. 查明根因的排错（含试过但无效的做法）；
4. 新的环境事实（端口、路径、版本、命令）；
5. 用户明确要求记下。

常规的写代码、改错字、看日志不记。

### 写入规则

- **先检索再写**：用标题与别名检索，命中已有页则更新该页，未命中才新建。一件事只对应一页。
- **读取不修改**：检索与读取不会改动页面；修改必须通过显式写入完成，历史由 Git 保留。
- **保留来源**：写入内容附带来源（日期、用户原话），以便日后核对。

## 7. 近期活动

- **一条活动**写"人在做什么、想通了什么"，不写"改了哪些文件"。每个会话最多一条，同一天同一主题合并。
- **近期摘要**固定约 10 行，分两段：近期主线（近 2～4 周，2～3 行）与最近 7 天（≤ 7 行）。
- **折叠**：主会话记录新活动时，服务返回当前近期摘要与已超出 7 天窗口的条目，主会话据此重写近期摘要，过期条目并入主线或丢弃。服务只校验行数上限，超出则拒绝写入。
- **活动记录**按月存放、永久保留，参与检索，可按日期筛选。

## 8. 画像与候选

- 用户明确要求记住的内容直接写入画像。
- 主会话观察到的可能偏好作为**画像候选**提交（规则文本、用户原话、日期）。服务用嵌入模型比对已有候选：意思相近则合并并累计出现天数，否则新建。
- 候选在不同日期出现满 2 天（可配置）才可确认。此时常驻区块提示有待确认的候选；用户执行 `review` 指令，主会话逐条展示，用户回答"是 / 否 / 改成……"。
- 被拒绝的候选进入**拒绝列表**，之后相近的候选不再提议。
- 画像设上限：档案 ≤ 15 行，协作规则 ≤ 20 条（可配置）。写入后超限则拒绝，需先合并或删除旧条目。
- 在任何目录都可能踩到的环境红线，各用一行写进档案；细节仍在对应细节页。

## 9. 常驻区块

- 常驻内容通过各客户端原生加载的全局规则文件注入。`tacit connect <客户端>` 绑定客户端后，服务在该文件中维护一个常驻区块，依次包含：画像、近期摘要、记忆规则、待确认候选提示（有候选时）。
- 影响常驻内容的写入会重新渲染常驻区块；结果未变不写文件；起止标记不完整或不唯一时拒绝改写；区块之外的内容从不改动。
- 正在进行的会话不会重新加载，新内容从下一次会话生效。

## 10. 运行方式

- 以单一常驻 HTTP MCP 服务运行；所有客户端连接同一服务，写入串行执行。服务未运行时记忆不可用。
- 配置在记忆仓库之外：`~/.tacit/config.yaml`（端点、模型名、上限、端口等）与 `~/.tacit/rules.md`（值得记标准，缺失时用内置默认）。

## 11. 不做的事（v1）

| 不做 | 原因或归属 |
| :--- | :--- |
| 任务交接（上次停在哪） | 由客户端负责 |
| 保存原始会话 | 由客户端负责 |
| 客户端钩子、后台补抽 | 写入只依靠记忆规则与记忆指令 |
| 主动浮现往事 | 细节只在被提起时检索 |
| 按项目的常驻内容 | 项目约定应写在项目自己的仓库文档中 |
| 目录式的位置地图 | 细节以线索检索为主 |

## 12. 扩展

本文为初版（v1）设计。扩展时遵守：

- **所有入口经常驻服务**：TUI、Web UI 等新界面只调用常驻服务，不直接读写记忆仓库或索引。
- **规则只有一份**：新能力先在核心实现，再由各入口调用。
- **文件始终可直接编辑**：界面是便利，不是必需。
- **配置向后兼容**：新增配置项必须有默认值。

已知方向：Web UI（浏览、审核候选、检索调试）、TUI、为不支持 MCP prompt 的客户端生成原生指令文件、按项目的常驻内容、更换索引引擎。
